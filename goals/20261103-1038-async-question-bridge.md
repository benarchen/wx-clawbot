本人确认的范围修订：异步问题为运行中补充输入，桥接保证本入口持久化单次提交；不保证电脑与微信的全局首答互斥。已知另端输入使未提交入口失效，未决竞争／多输入明确提示不确定或冲突，不猜测先后。要求强制等待或审批的动作继续使用同步原生确认或真实执行门禁。本修订仅替代跨端竞争保证，不取消即时通知、准确答复、严格输入分类、迁移、真实原生／手机及交付关卡。

## 1．目标、依据与原问题

目标：本人从微信发起的任务在 Codex CLI 中产生结构化异步问题时，微信在任务结束前收到完整问题；本人通过准确请求 ID 回答，答案进入准确原会话，状态和结果可核验。覆盖重复事件、跨项目、电脑抢先回答、轮次结束、断连、重启与提交未知等失败路径。

已核对的现场基线：Git HEAD 为 `38debfb0aa8fb1610c49ab58766d7f3e15884b7b`，本机运行 `0.1.1`／schema 5，原生运行时 `0.166.0`。工作区另有本人从微信安排的 MIT 许可改动，尚未提交；不能将 HEAD 当作整个工作区快照，不能覆盖或顺带归档这些改动。580 项是既有回归成绩，本轮实现后仍须执行对应完整回归，不将历史成绩写成本轮通过。

本次漏转问题的准确类型已核实：模型调用 `request_user_input_async`，原生读取结果为 `agentMessage`，包含 `delivery: "async"`、非空 `questions` 和原始 `item id`；题目含 `title` 及字符串数组或空值形式的 `options`。该消息当时标为 `phase: "final_answer"`，但后续工具与回答仍继续，任务最终完成。因此，phase 不能代替 turn 终态或待答状态。

现有 [interactions.py](../src/wx_clawbot/interactions.py) 处理 `item/commandExecution/requestApproval` 和 `item/tool/requestUserInput`；[execution.py](../src/wx_clawbot/execution.py) 未将上述异步 agentMessage 转为独立微信问题。[output.py](../src/wx_clawbot/output.py) 会将其拼入最终正文，现场冻结最终回执也含该问题，不能误记为“最终文本完全丢失”。实际缺陷是没有即时通知、准确答复入口及异步状态闭环。

原任务、thread、turn、call、问题和消息 ID，以及原始正文，仅用于私有核对，不进入正式 fixture、提交或公开文档。使用脱敏“公开署名二选一”场景复现。

## 2．范围与工程边界

### 2.1 本轮必须交付

- 精确识别结构化异步问题，及时通知，单题／多题及自由文本答复、准确绑定与持久化去重。
- 原生双向路径证明、答复意图先落库、结果分级、轮次竞争和恢复保护。
- `/answer <request-id> <answer>` 与 `/status`／`/status <task-id>` 的兼容扩展，现有同步审批与追问保持。
- 隔离自动测试、真实原生闭环、最少必要手机验收、显式迁移与受控加载、文档及交付收尾。

### 2.2 必须保持

- 接入原 iTerm2、原运行时和准确 thread，不复制历史、恢复替代会话或改用后台副本。
- 不重跑原任务，不将异步答复伪装为一个新的独立业务任务；不削弱 REC01 的占用、容量、unknown 保留及多输入歧义保护。
- 同步原生 server request 仍由其准确 request ID 与原生裁决处理；异步消息的 item ID 不是 JSON-RPC server request ID，不能交给原 `rpc.respond` 假装回答成功。
- 原输入、已冻结正文、旧回执、原生交互、路由与观察选择受保护；`focus` 与 `attach` 保持独立。已由微信发起任务的必要交互不能要求本人额外 attach 才通知。
- 发送意图与实际外部调用分离；超时／断连只能形成未知，不能推断未提交或自动重试。
- 开发在隔离候选中进行，考虑 editable 安装和子进程导入，不能依据“未重启”推断修改日常源码不会影响正在运行的服务。

### 2.3 明确不包含

- 不靠普通文字中的问号、关键词、模型推测或截图 OCR 构造可执行确认请求。未覆盖类型可以明确提示原终端处理，不能静默漏掉或生成虚假答复入口。
- 不将异步征询自动升级为命令审批、长期授权或可执行权限；不为本人代选、默认同意、回答或关闭请求。
- 不修改 Codex 全局配置、模型、认证、信任、Skills、插件或 hook，不自动升级 CLI／daemon。
- 不操作微信 UI、扫码、登录或用户工作终端；不继承旧批次测试消息授权。
- 不扩大至 Mac 完整排版／复制、同消息图文、自然上下文失效或其他原后置能力；不修改 MIT 许可工作成果及其决策。
- 本轮不自动支持任务完成后的跨轮次回答或静默开启后续任务。需要补充时，由本人明确发起普通后续任务，走既有目标复验与准入；这不叫恢复旧请求。

### 2.4 授权与启动规则

施工依据为本人明确开工及接受异步补充模式；ASK01 已创建，默认不委派，按检查点顺序执行。

真实测试只使用清楚登记的自有专用窗口，至多两个测试标签；测试输入只允许冻结标记、选项及零业务写入指令。原任务与用户工作会话仅只读取证，不向其中注入实验。

本机停止、真实迁移、部署与额外测试发送前，先准备准确文件／数据清单、影响、备份、恢复方案与测试内容，再按当时已有明确授权判断是否已覆盖。缺少对应授权时汇总一次具体请求，继续不依赖授权的工作。Git 提交、合并、tag、push 或 Release 属于独立授权，旧 REC01 发布授权不沿用。

## 3．必须先通过的原生准入关卡

G01 是硬关卡，不能先实现完整微信路径、最后才发现答案无法送回。

### 3.1 需要证明的内容

1. 真实原生事件如何携带 `delivery`、`questions`、item ID、thread／turn，出现于 `item/started`、`item/completed` 或其他准确事件的哪一阶段；不能仅凭事后历史存在就声称实时事件已接通。
2. 原 CLI 对这类问题提交答案时，实际使用什么协议、答案格式、身份前置和接收证据；本人答案如何进入模型可见上下文。
3. 电脑抢先回答、原轮次完成／中断、连接换代及发送超时分别产生什么证据；是否有足够信息拒绝过期或重复回答。
4. 答案是否作为同一 turn 的额外 userMessage 出现，以及如何与原业务输入区分；验证当前 `map_turn`／恢复逻辑会否误判合并输入。

### 3.2 技术路径与停止条件

- 首选现有受支持运行时的原生路径，不创建新的 daemon、thread 或替代工具。若准确答案路径是 `turn/steer`，必须使用准确 `expectedTurnId`，并真实证明它符合此类提问的交互语义。
- 官方文档说明 `turn/steer` 追加输入到活动轮次，轮次不匹配或无活动轮次时拒绝；它本身不证明异步问题已被处理，也不能直接推导为原生“首次答复获胜”。[官方接口说明](https://learn.chatgpt.com/docs/app-server)。
- 官方更新记录确认结构化异步问题通过 `request_user_input_async` 提供，但启用条件与客户端行为须按现场版本核验。[官方更新记录](https://learn.chatgpt.com/docs/changelog)。固定版本生成的 schema、真实请求／响应与模型最终标记才是本轮实现依据。
- 不使用 `thread/inject_items`、伪造工具返回、篡改 rollout／状态库、向 TUI 粘贴模拟答案或普通文字猜测代替正式答复协议。
- 本人已接受异步补充边界：原生没有问题级首答互斥及独立 resolved 信号；G01 须证明原轮次追加、错误／已结束轮次拒绝、连接失效不重试，以及跨端可见性窗口与冲突的真实限制。若连这些准确接收／失效证据都不能成立，仍保持 G01 未通过并停止依赖建设。不能把仅通知当成双向闭环，也不启用跨轮次新任务。
- G01 通过后先写入接口决策表：通知事件、请求键、答案线格式、成功含义、竞争判定、结束／断连规则、可支持版本与拒绝路径。关键接口不得留到实现时猜测。

## 4．既定交互、状态与数据契约

### 4.1 识别与路由

- 识别条件必须同时匹配已核验版本的结构化类型、`delivery=async`、合法非空 questions、准确 item／thread／turn，以及合法任务或观察来源。纯 async 消息但无 questions 不注册为可答复问题；未知／损坏结构只提示无法完整处理。
- 以原生来源、thread、turn 和 item ID 构成持久化唯一键，记录问题内容摘要与 revision。始终使用固定的原目标，不随当前 focus、数字列表、项目切换或重新发现结果重定向。
- 本桥接业务任务的异步问题按原任务通知；桌面主动任务只有原独立观察订阅授权的范围才通知。其他项目／未观察的桌面会话不采纳、不显示、不读取其正文。
- 异步消息 `questions` 的选项是字符串，不能沿用同步追问的 option 对象或 `isOther` 假设。无原生子题 ID 时生成稳定的桥接 `q1`、`q2` 等展示键，保留原顺序、内容摘要和版本，明确这些不是原生 request ID。
- item started／completed／重传／历史补核均汇入同一去重入口；不完整事件仅有界读取准确 item，不轮询全机历史、重复推送或重建旧问题。

### 4.2 展示与答复

- 完整问题先持久化，再原子创建优先级较高的冻结 Outbox 提示；包含项目、请求 ID、题目、选项、自由回答格式及本地有效期。异步卡明确“任务可能继续运行”，不宣称暂停。
- 保持显式 `/answer <request-id> <单题文本或多题 JSON>`。单题允许选项文本或自由回答；多题必须准确覆盖全部展示题键，不接受缺题、多题、模糊编号或不确定解析。
- `/status` 分列任务运行状态与待答数量；`/status <task-id>` 列出准确请求、题目摘要、提交状态、有效期和下一步。异步待答不直接将原任务改为同步的 `waiting_interaction`。
- 新回答只能沿 G01 冻结的原生路径提交。若属于准确原 server request 的答复，依原交互身份规则；若属于 steer 等新用户输入，则完整复验原终端／进程启动身份／TTY／可见线程／native session／cwd／运行时代次，不能凭旧订阅绕过新输入资格。
- 先提交答案意图和稳定 answer client ID，再发送原生调用；重复同文或相反答案均不产生第二次调用。不得将异步 item ID 当作 JSON-RPC id 使用。
- 本地有效窗口初定 600 秒，复用既有交互预算；须明确这是微信入口的本地期限，不宣称原生问题自动过期。期限只使该入口失效，不代答、不取消原任务、不释放仓库占用。G01 若证实有更早原生失效，采用更早期限，不延长原生有效性。
- 完整提示上限沿用 7000 字符，单答案 4000 字符、组合输入 32000 字符。初定每次至多 20 题；单条记录不超过 1 MiB，未结交互总数与总字节继续服从既有 256 条／16 MiB 预算，不能为新类型另开同等额度使总量翻倍。超限只发送固定的原终端处理提示，不提供截断后的答复入口。

### 4.3 回执及生命周期

| 状态／事件 | 必须行为 |
| --- | --- |
| pending | 问题已登记，显示可答复与有效期；任务仍按原生真实状态运行 |
| sending | 答案意图已提交且正在外部发送；拒绝其他答案 |
| accepted | 只有 G01 明确的原生接收证明才可到达；文案只说明已接受，不冒称模型已采用 |
| observed | 准确原 turn 历史出现已登记 answer client 且正文摘要一致；仅证明输入可见，不声称模型采用、问题 resolved 或全局胜出 |
| stale | 原 turn 已结束／中断、原目标失效、原生已处理或本地期限结束；说明具体原因，拒绝旧答复，不开启下一轮 |
| unknown | 调用可能已到达但结果不明；保留意图、身份和证据，禁止自动重发或改投 |
| 电脑抢先回答／竞争 | 观察到未登记输入时使未提交入口失效；已有提交则标记 conflict 并明确两端可能都被接受。原生存在 ACK 后不可见窗口，不承诺提前发现或原子拒绝所有竞争，不伪造 resolved |
| 断连／重启 | 不回放已发送或未知答案；历史可以只读核对。恢复为可答复必须具备准确原问题仍有效及目标完整核验，否则保持失效／未知 |

上述是方案语义，实际状态名与每条合法迁移在 G02 冻结；不得将“原生已收到”“模型已处理”“本人手机已收件”合并为一个成功标志。异步类型不依赖并不存在的 `serverRequest/resolved`，同步类型的该事件语义保持。

原 turn 完成使本轮答复入口失效，即使问题曾标为 final_answer，也不能提前将整个任务完成。需要任务结束后补充时，由本人明确发起新的普通后续任务，本轮不静默代发。若后续要求跨轮次可答复，须另行确认原生证据、准入、作用范围及用户文案。

### 4.4 任务关联、持久化和保留

- 同轮次答复是已登记问题的辅助输入。只有先落库且 thread／turn／item／稳定 answer client／内容摘要全部匹配的输入，才可纳入已验证辅助输入集合；其他多个业务输入仍按原规则保守 unknown。
- 不能通过忽略所有额外 userMessage、放宽所有合并输入或只看第一个 client 维持原任务 completed。结果恢复、迟到事件和外部任务采纳必须使用同一严格分类；占用释放保持 REC01 的独立终态证明，不因答复已接受提前释放，也不把结果歧义重新变为永久占用。
- 原任务仍只执行一次、只保有其准确占用；异步问题不是新的业务活动项目，不重占队列或旁路全局容量。答复中断与原任务终态分别记录，不将答复失败写成原任务重新执行。
- 优先在同一 RuntimeState／SQLite 单写入模型下增加一张最小异步问题表及必要索引，记录问题唯一键／摘要、原目标、revision、答复意图／摘要、稳定 client、接收证据、状态和时间。是否能安全复用原 interactions 表须先证明其启动 stale 规则、同步 RPC id 和异步语义不会混淆；不得为省表复用错误语义。
- 预计 schema 5→6；G02 先冻结准确 DDL、字段和索引，再编码。旧库启动仍不隐式升级，显式迁移必须维护锁、绑定、私有备份、完整性、外键、旧业务行与冻结回执逐表验证。支持旧版依序升级及重复无操作，不能用清库重新开始。
- 已发送、unknown、尚未处理及其去重证据继续保护；不靠重启或保留期重新开放回答。新 Outbox 正文一经冻结不改写，旧历史不重排或补发。
- 新最终结果与实时问题明确区分：已经通知的问题不再次作为待答卡发送，保留必要的提问及处置摘要，不删除其他真实最终正文。只在最终结果里补出问题不算即时通知通过。
