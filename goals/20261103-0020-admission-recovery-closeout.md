## 2．能力边界与授权

### 2.1 本轮必须交付

- 任务结果与仓库占用分离，自动对账、安全释放、持续阻塞说明及正式异常处置入口。
- 同项目、嵌套目录、同 Git common directory 和 worktree 的一致准入；保留同会话 FIFO、最多两个桥接活动项目和既有容量保护。
- 对全仓已跟踪代码、测试、配置模板、构建入口和文档进行检查，列出问题、证据、严重度、处理结果及复验结果。全面检查不等于无关重构。
- 交付可重建的测试、迁移／回退演练、运维操作卡、能力与限制清单、实际本机恢复证据及完整交接。
- 尽量由自动化完成验证；能从源码、账本、协议和现有截图查明的内容不交回本人逐项确认。

### 2.2 必须保持

- 未知任务不重放，发送未知不自动重试；不伪造 completed／cancelled／interrupted，不改写旧冻结结果、输入、目标、client／queue／thread／turn。
- 新派发仍完整复验当前终端、进程启动身份、TTY、Session ID、cwd 和原生运行时；历史占用对账不能产生新路由资格。
- `/focus` 与 `/attach` 独立；审批与追问固定准确请求及代次，原生裁决首次有效回答；取消与中断以原生确认区分。
- 单消费者、SQLite FULL、意图先提交、终态与回执原子性、有界队列和结果资源限制保持。
- 仓库占用只是桥接准入，不是全机文件锁。不能阻止用户或独立客户端在核验后自行发起任务，也不能证明历史子进程已全部退出。
- 结果 unknown 即使释放占用，仍受原 unknown 的保留、附件保护和禁止自动重跑规则约束。

### 2.3 明确不包含

- 不建设 Web UI、云服务、多用户、群聊、多 Agent 编排，不增加核心依赖或无行为的框架层。
- 不恢复本轮之外的三项后置能力：自然上下文失效触发、Mac 完整排版与复制、同消息图文。
- 不操作微信 UI，不复用旧批次测试消息授权，不登录、扫码、自动接受提示或重试退出的客户端。
- 不接管或停止用户工作终端，不修改 Codex 全局配置、信任、认证、模型、Skills、插件或 hook；过去的临时设置授权不沿用。
- 不因“全面整理”删除来源不明目录、旧证据或用户文件；不访问其他独立项目的配置、凭据和服务。

## 3．既定流程与数据决策

### 3.1 任务结果与占用分离

保留 `tasks.state` 的真实执行结果语义，不新增一个会被当作成功的“已处理”任务终态。为已取得准入的任务增加独立、持久化的占用记录：至少包括 task_id、holding／released、revision、原因码、核验来源与时间、连接身份摘要及证据摘要。处置事件追加审计，不覆盖历史决策。证据只保存必要 ID／状态与摘要，不保存额外消息正文、认证或完整工具输出。

使用最小必要结构，预计 schema 4→5；DDL、索引、约束和迁移链在 G01 冻结，不能在日常启动隐式升级。旧非终态已提交任务保守初始化 holding，received 不因升级获得派发许可；已有终态不新增占用。新任务在调用原生提交前原子取得占用；提交结果不明时占用保持。

任务列表区分“需执行／待核验的活动工作”和“保留的历史未知记录”。已释放的 unknown 不再消耗两个活动项目、同会话十条排队及全局 128 条活动额度；仍 holding 的 unknown 和 received 等真实活动继续计入。历史未知分页查看，不能为了读取完整历史而使准入扫描无界，也不能截断持有者视图后放行。

结果恢复优先：先按原有完整身份及 client／turn 唯一条件恢复可确认结果，再对仍为 unknown 的记录核验占用。释放占用不能令记录退出所有结果恢复路径；显式刷新通过独立部分索引分页继续严格结果对账，不把占用证据直接当作结果证明。

### 3.2 自动释放的证据标准

| 证据 | 结果 |
| --- | --- |
| 准确 client 唯一对应原生终态，且原生提交／排队无在途不确定性 | 按现有规则确认任务终态，释放对应占用 |
| 旧 turn 明确包含多个合并输入，原生终态已确定，所有相关已知提交和队列均核清，无继续执行或迟到提交风险 | 可只释放这些关联任务的占用，任务结果继续 unknown；不得拆分或编造各自结果 |
| 查询不到旧记录、有限历史窗口内未发现、分页未完成、原生不可达、身份冲突、只看到线程 idle 或队列暂空 | 证据不足，继续 holding，并说明原因 |
| 排队、执行、等待审批／追问、停止尚未确认、提交 ACK 丢失或尚有提交调用在途 | 继续 holding，禁止凭超时释放 |
| PID 消失、窗口关闭、socket 路径变化或等待天数增加 | 均不能单独证明安全释放 |

历史查询只使用已保存的原始 thread／turn／client／queue 身份及已核验的原生只读协议；不得调用 resume／restore 创建或加载替代会话，也不得读取不相关私人会话。若需要放宽现有“必须有活跃原终端才能读历史”的限制，先在项目契约明确：历史核验仅能形成占用证据，绝不恢复旧目标、订阅或派发资格；原生来源不能验证时仍保持 holding。

证据不能仅依赖模型最终文字或正文中的“完成”。必须来自结构化原生状态。中断不保证系统子进程退出；已经发现相关子进程或工具仍在运行时继续阻塞并报告，不能以 turn 终态掩盖已知风险。

### 3.3 竞争与生命周期

- 继续由唯一执行协调器串行处理仓库准入；原生 RPC 在数据库事务外完成，落库时比较 task／hold revision、原生连接代次和相关任务快照，失配就丢弃证据并重新核验。
- 同一仓库多条旧记录分别核验；释放其中一条不能绕过另一条 holding。合并 turn 的多条占用在同一决策事务中核对和处置。
- 释放与新任务取得占用保持原子次序；commit 失败不得放行。取消 received 与准入竞争，只能“未提交取消”或“已进入原生流程”之一，不双执行。
- 释放后迟到的 ACK／started／queued 事件必须校验原关联。若表明原证据失效，立即持久化冲突并阻止同仓库后续新增派发，不删除审计，不把迟到事件当新任务重投，也不自动中断已执行任务。
- 重启恢复继续使用持久化占用和处置 revision；不能因为 `tasks.state` 仍为 unknown 就重新初始化已经释放的占用。缺失／损坏的占用记录按安全拒绝处理。

### 3.4 等待、重核与通知

- 每条等待任务持久化阻塞者、项目／仓库摘要、原因码、首次等待、最后核验和通知状态；普通回执显示准确阻塞任务及可执行下一步，不暴露无关项目或私人路径。
- 启动、重连、相关终态、占用处置和新准入触发核验；同一原生 thread 合并重复检查。后台按 1／2／5／15／30 秒退避，单次检查截止 5 秒，查询分页和并发有界；超过查询预算返回“证据不足”，不冒充无任务。
- 首次等待立即提示，持续 60 秒仍阻塞时最多追加一次升级提示。阻塞原因实质变化可以更新状态，但不每秒发送；通知去重持久化，重启不重新刷屏。通知期限只决定提示，绝不决定释放。
- `/status` 和 `/status <task-id>` 能区分未提交等待、真实执行、历史结果未知但已释放、未知且仍持有；原生离线时仍能给出最后核验及过期说明。
- `/stop <received-task-id>` 仍可随时本地撤销，不要求原生在线；继续等待是默认行为，不自动取消或重发原任务。阻塞解除后仅在冻结目标复验通过时推进原 received 意图一次。

### 3.5 正式人工处置入口

首选本地 CLI，避免新增微信权限面。计划提供 `wx-clawbot admission-report --task-id <id>` 和 `wx-clawbot admission-release --task-id <id>`；最终命名在 G01 冻结并由 help／文档／测试共同校验。

- report 和 release 默认只读；执行须显式 `--apply`、准确任务、处置理由及与报告绑定的 revision／确认摘要，不提供“一键释放全部”。
- apply 不能绕过消费者锁直接改运行库。沿用本项目单写入模型：维护模式先正常停止桥接、取得同一消费者锁；需要原生证据时仅建立受支持的只读连接。记录停服影响并在明确授权后执行。
- 发现真实活动、排队、未决提交或证据变化时拒绝；重复 apply 幂等，过期报告／错误任务／错误绑定／错误仓库均拒绝。
- 人工入口确认的是占用处置，不把 unknown 改成完成。原生不可达或证据不足时只提供报告和所缺证据，本轮不提供无条件 force 绕过安全门禁；确需风险豁免时另行明确范围与后果，不在施工中自行增加。
- 自动核验已经能证明安全时不要求本人操作；人工入口是少数异常的正式补救，不是日常使用步骤。

性能与容量补充：在同机、同依赖、同固定输入下成对比较原版与候选。至少覆盖 1 千／1 万／10 万条终态与 released unknown，以及 0／128 条真正活动；预热 1 次、各取 15 次，报告中位数、p95、最大值、查询计划和原始样本。准入查询不能随无关历史全表增长；128 个活动边界仍读全。新增自动核验在退避上界下每 thread 至多一次／30 秒，事件触发去重，空闲且无待核验记录时不额外扫原生历史。正常本地控制处理 p95 小于 1 秒，RPC 超时不占满事件消费路径。测量波动时同条件成对复验一次；不得自行降低标准或宣称未经对照的性能提升。
