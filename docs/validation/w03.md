# W03 真实接口验证

本轮使用两个临时项目与专用可见终端，CLI 分别为 0.163.0、0.164.0，daemon 为 0.164.0。微信通道没有参与；本文的“桥接”指本地原生协议测试驱动。机器可读结果见 [w03.json](w03.json)。

## 已观察并复核的行为

| 对象 | 方法与实际结果 |
| --- | --- |
| 审批先答 | 两个独立连接收到相同原生请求。桥接先批准、电脑先批准均真实执行一次，另一端等待解除；相反的迟到答复没有改变结果 |
| 审批竞争 | 对已显示的同一请求并发发送电脑 Enter 同意和桥接取消；得到一个原生 interrupted 结果，追加写入文件没有创建，未产生重复 turn。不以两端本地时间判定赢家 |
| 多题与文本 | 原终端实际显示两题等待表单后，桥接答复一个选项及一份自由文本；原生模型回显两值，表单关闭。本人已确认首版采用多题单选与自由文本，同题复选后置 |
| 电脑先答追问 | 原表单默认选项由电脑 Enter 提交，原生回显该选项。错误问题 ID 被桥接拒绝，已处理入口关闭；另一连接迟到发送相反选项未改变答案 |
| 过期与断连 | 已过期答复和断连旧代次不发送；重连后重新核对同一原生等待请求，生成新的公开 ID，取消获原生确认且没有创建目标文件 |
| 追问取消 | 对真实表单测试过期答复拒绝，再由电脑 Esc 取消，收到原生 interrupted 终态；迟到答案不恢复任务 |
| 排队与取消 | 真实保留十条 daemon 队列输入，桥接拒绝第十一条准入；八条原生删除获确认，剩余两条按 FIFO 分别生成独立 turn，client ID 与队列一致 |
| 运行中断 | 专用命令先写 running 文件，再等待并准备延迟写入。运行已证实后发 turn/interrupt，收到 interrupted；超过原定写入时刻仍没有目标文件，被删队列任务均未执行 |
| 回执丢失 | 入队帧发出后仅断开该侧车，调用结果为 unknown；通过原生队列查询稳定 client ID 找到唯一提交，未重发，随后原生取消成功 |
| 配置与身份 | 两终端、进程启动身份、TTY、运行时代次、native thread／session、项目与模型持续复核；全局配置保持唯一授权信任增量后的摘要 |

交互模块不把“答复帧已发送”当成原生已接受。`awaiting_native` 必须等待原生 resolved／终态；发送结果未知时不能换一个相反答案重试。resolved 不说明哪端获胜，界面只据此关闭待答入口。

## 原 TUI 队列反例

两个 CLI 版本都真实复现：运行门控任务时，桥接通过 `thread/queue/add` 追加第一条任务，电脑在原 TUI 使用 Tab 追加第二条；原生队列查询只有桥接条目。门控结束后，实际历史出现一个同时包含两条 userMessage 的 turn，最终只回答后一个标记。

因此，“原 TUI 的 Tab 与桥接自动统一排队”未通过 V04。不能以收到全部文本、没有重复消息或两个任务进入同一 turn 认定各自独立执行成功。

已另行真实验证官方 `codex queue` 的专用桌面入口：可见普通 Shell 把电脑任务加入同一 daemon 队列，返回真实 queue ID；桥接与电脑任务按同一快照顺序独立完成，原 TUI 持续显示结果。其正式体验在 [入口提案](../desktop-queue-contract.md) 中明确，不能冒充原按键行为已修复。

源码对应：[TUI 本地队列](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/tui/src/chatwidget/input_flow.rs)、[turn/start 使用 start_or_steer_turn](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/turn_processor.rs)、[官方 CLI queue](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/tui/src/session_queue_commands.rs)。`canAcceptDirectInput` 是原生所有权能力，没有提供本项目可设置的 TUI 队列锁，不能把它当作忙碌排队开关。

## 启动修正与无效样本

启动器曾增加 `-c check_for_update_on_startup=false`，专用 W03 终端因此进入独立运行时。已在提交实现前删除该参数，随后新终端真实核对为同 daemon；原失败样本只执行就绪检查，未用于审批成功证据。[官方选择条件](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/tui/src/daemon_startup.rs) 明确一般 `-c` 覆盖会排除共享 daemon。必须在启动后核验实际运行时，不能依赖命令格式推断成功。

初次中断脚本错误地等待未观测到的 outputDelta，命令正常结束并写入测试文件，该样本没有计入中断通过。后续用明确的 running 文件证明实际启动，再验证原生 interrupted 与延迟文件缺失。UI 自动测试也改为实际界面就绪轮询；两次在按 Tab 前停止的 0.164 样本未算作原 TUI 队列反例。没有重放未知任务或修改全局设置来掩盖这些失败。

原有 hooks 的 code 7 警告仍存在；本轮没有读取、修改相关 hook 或将其报告为成功。模型任务、审批和中断的结论分别按原生状态核对。

## 检查入口与边界

离线入口为 `python -m unittest discover -s tests -v`。不会自动连接微信或用户终端。显式现场审计器只读连接已存在的专用测试端点，检查私有记录关联的真实原生历史与文件效果：

```sh
.venv/bin/python tests/integration/w03_verify.py --live \
  --primary-record /absolute/path/to/private/primary.json \
  --comparison-record /absolute/path/to/private/comparison.json \
  --report /absolute/path/to/report.json
```

私有记录保存启动身份、请求和屏幕观察，不能提交到公开仓库。审计器重新读取当前端点、原生历史、效果文件和队列；历史 UI 展示根据现场观察记录审计，不声称只读重查等于再次执行了所有竞争场景。V04 按原 TUI 与桥接的两条输入是否形成按序、独立且各自完成的 turn 判断，不提供以专用入口替换硬要求的参数。专用入口成功仅作为单独实证，不能覆盖原 TUI 场景失败。

本轮没有测量控制处理 p95、微信网络延迟或常驻资源趋势，不能将目标性能写成结果。微信收发、项目路由、真实项目使用与故障恢复仍按后续 Goal 验收；当前完整进度仅见 [ROADMAP](../../ROADMAP.md)。
