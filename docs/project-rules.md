# 项目规则加载责任与当前边界

本文定义本人已明确接受的“原生限制方案”，记录 AUD01 的源码与真实原会话验证。当前状态见 [ROADMAP](../ROADMAP.md)，要求和验收见 [AUD01](../goals/20261104-2338-native-diagnostics-rules.md)。工程验收后，日志修复已按本人后续授权切换到本机独立 0.1.4，见[本机记录](validation/aud01-local-deployment.md)；本页的原生规则限制仍然适用。

## 当前责任

桥接核验原终端进程、可见 thread、原生会话／运行时代次和 cwd，再向同一原生队列提交任务。桥接当前不发现、复制或注入规则正文，没有规则版本检测、热更新确认或“模型已采用新规则”的回执。启动提示要求读取 AGENTS.md，不能替代逐轮刷新证明；重新连接或 `/focus` 也不构成刷新保证。

Codex 负责原生指令的发现、缓存、优先级和模型上下文。文件当前摘要、原生加载快照和模型行为是不同对象：摘要变化不证明刷新，模型复述标记也不是规则来源证明。

## 操作边界

修改项目规则后，不把原会话仍可输入、桥接重连或文件摘要变化当作新规则生效。涉及执行边界的规则变更，应先停止向该会话新增普通任务，在原生端按受支持方式处理，再完整核验目标；桥接没有 `/reload-rules` 命令。

需要新建可见会话时由本人明确选择，并作为新会话核验；不自动取消、迁移或重放原队列。新会话也应核对其加载来源与版本，不以一次模型复述作为充分证据。

真实实验固定同一进程、TTY、thread、native session 和 daemon 身份，九个 client 各自唯一关联一个 completed turn；完整历史另核对启动握手加九轮共十轮，只有 userMessage／reasoning／agentMessage，没有工具调用。队列变更案例在写文件前后均确认同一输入仍处于队列。其后仅关闭自有测试终端，原有两个终端、生产进程／argv 及四份配置摘要保持。机器摘要和[交付记录](validation/native-diagnostics-rules.md)保存脱敏证据。

## 已确认的原生限制契约

本人明确选择接受原生限制方案，满足施工清单 A06；原清单中的路径 L 仅是此方案的内部编号。依据匹配源码和真实反例，原设计的逐轮项目规则刷新要求正式替换为以下契约：桥接继续保证准确身份／cwd 和原生队列，不承诺原会话规则热更新、规则变化检测或自动阻断；修改项目规则后，由本人明确选择新建可见会话并重新核验来源，旧队列不自动迁移、取消或重放。新会话仍服从原生信任、权限和大小边界，不承诺模型必然遵从每条规则。

如果未来要求桥接主动检测规则变化并阻断任务，需另行确定覆盖范围、初始加载版本证据、队列与竞态语义，不能把文件摘要检测说成原生刷新证明。本轮不建设扫描器、阻断器或规则注入，不把此类能力列为已实现。

本次决定仅确认责任与能力边界，不授权生产切换、外发微信或 Git 发布；候选日志修复的部署仍按独立运维授权执行。
