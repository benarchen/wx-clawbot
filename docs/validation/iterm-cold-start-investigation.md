## 实现缺口与证据边界

修复前，[HostLifecycle.ensure](../../src/wx_clawbot/hosts/lifecycle.py) 在按需 open 后，只等待 iTerm2 进程身份出现；随即调用 backend.connect。进程出现不证明 API 已可连接。[无授权 UI 的传输预检](../../src/wx_clawbot/hosts/lifecycle.py#L59) 遇到连接失败立即抛出 connect；ensure 同样立即结束当前请求，没有在冷启动窗口等待传输就绪。[命令处理](../../src/wx_clawbot/controller.py#L157) 因此尚未走到创建阶段就返回错误。

15 秒连接超时是单次连接的耗时上限，不会使立即发生的连接拒绝自动等待 15 秒。现场约 0.245 秒的失败时间与这条缺少等待的路径一致。原日志未保留此次底层连接异常，无法再区分 Unix socket 尚未就绪、端点残留或其他瞬时传输错误；不将其无证据归因为授权拒绝或 API 未启用。

使用真实 HostLifecycle 及离线替身模拟“进程出现、第一次 connect 暂不可用、下一次可用”：首次 ensure 仅调用 connect 一次即失败，第二次 ensure 在不再 launch 应用的情况下成功。复现通过，零真实应用启动／原生提交，不能替代修复后的冷启动真机验收。

v0.1.3 至 v0.1.4 的上述 lifecycle／controller 文件无变化；这是已有冷启动边界缺口，不是本轮脱敏日志改动新引入的代码差异。现有并发启动测试将 connect 设置为立即可用，没有覆盖“进程先出现、API 后就绪”。

## 建议修复与验收

在首次按需启动及当前准确进程的初始化窗口内，给无授权 UI 的传输就绪检查设置有界等待和退避，复验同一进程身份；就绪后再进入授权连接及原命令的后续创建阶段。总耗时应纳入现有命令期限，不用固定盲等或无限重试。

仅等待创建前的可重试传输状态；明确授权拒绝／未完成、应用换代或超时应停止，不能重复弹授权、重放创建或复用未知启动。保留后台不自动拉起应用、并发只 launch 一次、现有 unknown 不重放语义，不自动关闭或接管应用打开时的普通 Shell。

必要验证：进程先出现而 API 延迟就绪时，同一条命令最终创建且仅创建一次；API 一直不可用、授权未完成、进程中途变化、并发请求和创建结果未知时均保持边界。离线失败回归通过后，再用明确授权的专用终端执行一次真实冷启动，不操作微信 UI 或额外发送测试消息。

## 2026-11-05 22:05 修复与离线验收

在 ItermBackend 增加 wait_ready：仅使用已有禁用授权 UI 的传输探测，在准确进程身份下最多等待 5 秒；暂时的 connect 失败按 0.1、0.2、0.4 秒及最高 0.5 秒间隔退避，成功前后复验进程。进程变化／消失、非 connect 错误和取消立即停止，超时返回原连接失败语义，不请求授权或创建终端。

HostLifecycle 在未持有可用连接的按需请求中，先执行该等待，再连接和授权。等待与连接共用原有 15 秒连接总期限，命令层原有 25 秒宿主截止时间不变；不是额外叠加 5 秒。已连接请求直接复用，后台恢复仍不拉起应用，也不进入这段显式等待；授权连接、创建及未知操作均未增加重试循环。原进程出现后的探测与后续连接之间仍可能发生故障，失败会按原语义停止，不承诺消除所有启动竞态。
