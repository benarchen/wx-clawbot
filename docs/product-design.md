## 1. 产品定位

PRJ01 在既有 MVP 上新增已确认的项目管理旅程：设置项目总目录、预览并确认一层目录注册，本机／本人微信查询、注册与取消注册已有目录，变更即时生效而不切换对话。本轮已完成离线、专用原生及本人手机验收，随 0.1.11 公开交付，准确命令、限制与验收见[专题](project-management.md)和[施工清单](../goals/20261108-2048-project-management.md)，原 P01 至 P14 保留。

通过本人手机微信，选择本机注册项目中的准确 Codex 原生会话，提交工作、查看结果、回答追问、处理审批和停止任务。项目文件留在原目录，原生对话保留自己的历史与上下文；iTerm2 提供可见创建和桌面操作入口。

痛点是离开电脑后不方便继续某段本地工作，以及多项目、多对话间容易混淆目标。桥接负责明确选择、关联任务、控制与可靠回执；Codex 负责理解并执行获授权工作。截图仅为交互背景，不作为本项目实现证明。

产品价值以选对原会话、看懂执行状态、异常不误重跑为核心。微信目标独立选择，电脑切换画面不会被动改变手机目标。

NCM01 自 0.1.12 提供：通过微信查询／显式设置所选准确会话的模型、推理强度和 Fast，独立原生 status 以及现有 help 新分组；不修改全局默认或改变桥接已有命令语义。统一命令在 0.169.0 原生及本人手机功能验收通过，源码及本机正式独立制品均为 0.1.12，部署保护结果见版本记录。本人接受拒绝已知忙碌但披露桌面检查后竞争，Fast 仅证明原生设置确认，契约见[原生命令](native-controls.md)。默认输出优先用户决策：简明中文状态、模型分组、突出剩余额度，隐藏 token 诊断及重复技术字段；必要操作编号和未知风险不能因美化省略，详见[展示约定](native-controls.md#默认展示约定)。

## 2. 用户目标与首版边界

### 已确认

用户只有已绑定的本人。电脑须开机、联网并运行桥接；执行依赖受支持的既有 Codex daemon、已加载且可核验的对话及注册项目。新建可见对话还依赖 iTerm2 Python API 和必要的本人授权。睡眠、断网、关机期间不保证在线。

### 六项问答决策

| 编号 | 当前有效的产品决策 |
| --- | --- |
| D01 | 微信选择注册项目范围内、准确运行时中已加载的原生对话；不从标题、目录或时间猜身份 |
| D02 | 微信与电脑可操作同一原生对话；微信选择独立于桌面显示及终端存活，可用性由原生核验决定 |
| D03 | 既能选择已有对话，也能在 iTerm2 可见创建；新窗口出现不等于接入成功 |
| D04 | 微信与桌面专用排队入口共用原生队列；停止、查询和交互答复独立处理，原 TUI 按键保持原生语义 |
| D05 | 同步审批／追问由原生请求裁决首次有效答复；异步补充不具备此保证 |
| D06 | 初始验收先用两个临时项目，再按具体授权在 guixu 与 wx-clawbot 验收；不据此授权后续任意真实测试 |

2026-11-07 的 D02 澄清及 TGT02 确认取代早期必须跟随桌面、必须显示页脚 ID 的推断。现行依据见[原生身份契约](native-session-identity.md)。

### 首版设计范围

- 本人绑定与收发、注册项目和合法目录选择。
- 既有已加载对话发现、单次派发、持续选择、独立观察及可见新建。
- 原生排队、进展、文本结果、同步审批／追问、取消和恢复核对。
- 单张静态 JPEG／PNG 入站，原会话处理并返回文本；版本、模型和验收条件见[兼容矩阵](protocol-baseline.md)。
- 用户级托管、状态、诊断、独立制品与显式账本维护。

### 后续扩展

多用户／群聊、云服务、Web UI、其他 Agent／宿主、多 Agent 编排、语音、预约任务、任意外部通知 API 和通用插件市场不属于当前范围。这是边界说明，不构成已承诺路线。

### IMG01：入站静态图片扩展

单图沿用接收时的执行目标。跨消息不自动拼接；图片后发送的说明是下一条独立任务，依靠同一原生上下文理解。同消息图文、多图、动态图片、其他媒体和图片结果回传不在已交付范围。限制、失败和生命周期由[图片指南](image-input.md)维护。

## 3. 用户理解模型

| 概念 | 含义与边界 |
| --- | --- |
| 项目／目录 | 注册的本地工作及其合法 cwd；路径登记不是操作系统权限沙箱 |
| 会话 | 一段 Codex 原生对话，可理解为一个 Codex session；程序以完整 thread 区分准确对话，native sessionId 可能为派生对话共有的根身份 |
| 终端／TUI | 桌面操作界面；窗口不等于永久对话，后台列表不证明当前显示哪个窗口 |
| 执行目标 | 微信明确选中的会话；普通消息发往它，不随桌面变化 |
| 观察订阅 | 接收指定对话后续桌面主动任务事件；不改变执行目标 |
| 任务 | 一条已接收工作意图；目标在接收时固定，后续切换不迁移 |
| 执行／占用／送达 | 三种独立事实：原生结果、仓库准入保护、回执发送，不能互相推导成功 |

## 4. 命令与交互

| 用户目的 | 命令入口 | 关键反馈 |
| --- | --- | --- |
| 看项目、选目录 | `/projects`、`/cd <项目或路径>` | 项目、目录、受管会话；无匹配时可能可见创建 |
| 看已有对话 | `/sessions [关键词]`、`/ss` | 列表序号、稳定编号、来源和目录；纯查询，保留输入目标和观察订阅，不启动宿主 |
| 单次／持续输入 | `/send <序号> <指令>`、`/focus <序号>`、`/unfocus` | send 不改变焦点，focus 成功后普通消息持续发往目标 |
| 独立观察 | `/attach <序号>`、`/detach` | 真实订阅确认后成功，退订保留执行目标和已接收任务 |
| 可见新建 | `/new [标题]` | 当前目录内新对话，准确握手后选中；未知启动不自动再建 |
| 状态／停止 | `/status [任务ID]`、`/stop [任务ID]` | 执行、占用、投递可辨，原生确认后才能报中断 |
| 同步决定／回答 | `/approve <请求ID>`、`/deny <请求ID>`、`/answer <请求ID> <答案>` | 准确请求、期限和类型校验；过期或已处理明确拒绝 |

完整别名、快照期限和错误行为见[命令契约](command-contract-proposal.md)。未知 slash 命令不当作 Shell 执行；裸选项文字按普通输入处理，不能猜要回答哪个问题。

## 5. 典型使用流程

以下为操作示例，序号须使用本人刚取得的列表，不是已发生任务记录。

### 场景 A：微信进入项目并推进工作

先按 README 完成配置、本人绑定与运行准备。发送 `/cd sample-one`，等待准确就绪后发“检查脚本重复实现，先给建议”。实施时再明确范围，例如“落实第二项并自测，不提交”。路径无效、原生不可用或启动未确认时明确提示，不把准备回执当作完成。

### 场景 B：切换项目并返回

使用 `/cd sample-two` 进入另一受管对话，再 `/cd sample-one` 返回可核验的原受管对话；原对象不可用则提示处理，不复制历史制造连续性。已接收任务仍属原目标，结果标注来源。

### 场景 C：操作电脑已有终端

`/sessions sample-one` → `/focus 2` → 普通任务；或 `/send 2 指令` 只派发一次。列表覆盖注册根和已知准确 cwd，不递归搜索全部子目录。电脑同一 TUI 从 A 切到 B，微信仍选 A；A 若仍加载且核验通过可继续，卸载／断连则失败提示，不暗中改投 B。

### 场景 D：独立观察桌面任务

`/focus 2`、`/attach 1` 后，普通任务发往 2，同时观察 1 后续桌面任务。`/detach` 后仍向 2 输入。订阅失败保留原状态，不能只改本地标记报成功。

### 场景 E：跨项目审批

微信选 B 时，A 的准确已订阅原请求仍标注 A、任务、请求和具体操作。按 ID 决定只回 A，B 不变。同步两端先答和竞争均由原生裁决；异步问题提示任务可能继续，答案只是补充，不授权执行。

### 场景 F：电脑与微信共同排队

忙碌时桌面在另一个普通 Shell 使用核对过的 `codex queue`，微信任务进入同一 daemon／thread 原生队列；各条输入应关联独立结果。原 TUI Enter／Tab 可能引导或合并当前任务，不属于统一排队入口。[桌面排队契约](desktop-queue-contract.md)保留实测反例和选择依据。

### 场景 G：停止与故障恢复

先 `/status <完整任务 ID>`，再 `/stop <完整任务 ID>`；未提交等待可本地撤销，排队移除和运行中断分别等待原生确认。断连或回执未知先核对，不因没收到结果就重发任务；投递失败只处理原结果。重启后复验选择，旧数字列表和交互入口不沿用。

## 6. 回执与可理解性

项目、会话／任务标识、状态和下一步必须可辨。接收、入队、原生终态、API accepted 与本人手机实收分别表述；没有证据不宣称已读、检查通过或 Git 操作完成。

最终正文保留原生最终回答和错误；进展合并，错误优先保护，长结果有序分段。展示与复制见[排版专题](wechat-markdown.md)。旧冻结回执不因升级重排或自动重发。中断确认不代表已启动的全部系统子进程都已结束。

## 7. 产品约束

准确身份、未知不重放和本人绑定是安全约束。注册路径不限制 Codex 的所有系统权限；执行仍遵守原生沙箱、审批和项目规则。桥接不自动改全局配置、模型、认证或其他服务，不复制历史或恢复 notLoaded 存档冒充持续接入。

规则采用[原生限制契约](project-rules.md#已确认的原生限制契约)：不承诺热更新、变化检测或自动阻断。规则改变后由本人明确新建可见会话并复验，旧队列不自动迁移／取消／重放。模型费用和联网沿用原路径，桥接不提供模型额度。

当前并发、容量和保留期由实现限制，准确数值见[账本](state-schema.md)和[身份契约](native-session-identity.md)，不再称实施前待确认默认值。外部客户端仍可自行启动工作，桥接准入不等于全机互斥。

## 8. 首版验收

编号保持原产品验收身份；每条同时给出用户故事和可判定验收。核心项为必要要求，扩展仅在能力门禁内适用。实际覆盖与证据见[追溯矩阵](requirements-traceability.md)，本表不重复进度。

| 编号／优先级 | 用户故事与前提 | 正常／失败行为及通过条件 |
| --- | --- | --- |
| P01／核心 | 本人希望从绑定微信收发 | 同一确认对象收发；未知身份、群聊和不完整消息拒绝，不派发任务 |
| P02／核心 | 多项目工作者希望切换并继续 | 注册 cwd 正确、对话不串线；仅复用可核验受管会话；规则责任遵循原生限制，不承诺逐轮重载 |
| P03／核心 | 用户希望目录操作不越界 | 空值、不可访问、越界符号链接拒绝，保留原选择，不改其他任务 cwd |
| P04／核心 | 用户希望发现并单次发给既有对话 | 来源真实、完整身份无歧义；准确 thread 执行，send 不改焦点；不要求当前桌面显示 |
| P05／核心 | 用户希望连续操作且可退出 | 输入到显式目标，桌面变化及 sessions 查询不改投；unfocus 显式清除输入目标，原生失效明确提示 |
| P06／核心 | 用户希望从微信可见创建 | 合法目录、自有启动进程、唯一原生完成握手；两端同一会话；重复意图不重建，超时／歧义不伪成功 |
| P07／核心 | 用户希望获授权工作实际完成 | 专用临时项目真实修改和验证；差异、检查、失败可核对，不扩大项目授权 |
| P08／核心 | 用户希望两端处理同步决定 | 两端先答、竞争、超时、断连迟到和跨项目不串线；原生一次有效决定；多题单选与自由文本，同题复选后置 |
| P09／核心 | 用户希望有序工作且能停止 | 两端专用入口共享原生队列、各自 turn／结果；切换不迁移；本地撤销／队列删除／中断分别确认，说明子进程风险 |
| P10／核心 | 用户希望故障不重复执行 | 稳定入站去重，提交未知只读核对；发送失败只处理结果，未知发送不自动重试 |
| P11／核心 | 用户希望长结果可读 | 分段有序、错误保留、进展有界；Android 已验范围与 Mac 缺陷区分，复制按证据判定 |
| P12／核心 | 用户希望配置和私人数据受保护 | 桥接不自动改全局配置／其他服务；凭据、身份、会话和消息不入仓库；历史单次授权不成为常驻权限 |
| P13／核心 | 用户希望恢复后能判断真实状态 | 通道与依赖分报；身份及订阅复验后恢复选择，旧请求失效，unknown 不重跑，存活不冒充可派发 |
| P14／边界 | 维护者希望扩展不伪装能力 | Codex 能力显式声明，不支持返回 unsupported；替身核对边界，不安装第二真实 Agent，不承诺无代码接入 |

单图和异步补充使用 IMG01／ASK01 原编号单独验收，不改 P08 同步语义。V00 至 V08 的动态关卡见[开发契约](development-contracts.md#9-关键接口验证关卡)。
