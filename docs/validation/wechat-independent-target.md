# TGT01：微信独立选择原生会话交付

本人于 2026-11-07 明确要求实施微信独立选择：桌面焦点或同一终端切换对话不改变微信目标；原目标不可可靠接入时给出提示。施工范围与验收标准见[清单](../../goals/20261107-1027-wechat-independent-target.md)。候选已通过真实原生流程，尚未提交或部署，日常服务继续使用已发布制品；进度以 [ROADMAP](../../ROADMAP.md) 为准。

## 根因与实际改动

W05 当时为避免同进程 `/new` 后把旧 thread 误当成当前显示的会话，要求每次派发匹配页脚，并在发现刷新时用当前可见结果替换目录。这是当时的工程校验，没有证明用户要求微信自动跟随桌面。

- `sessions.py`：首次关联显式要求匹配页脚；后续准确绑定独立复验原终端／进程、运行时代次、thread、native session、cwd 和原生加载状态。原生查询后再次核对进程和运行时代次，拒绝查询期间退出／换代。
- `catalog.py`：完整发现成功后保留仍能独立复验的旧绑定，同时发现桌面 B；旧加载列表本身不能创建 A 的来源关联，失败发现不提交不完整目录。遍历保留绑定时使用快照，避免并发启动登记导致字典迭代中断；该失败已先由回归复现再修复。
- `hosts/visible.py` 与 `controller.py`：已 ready 的受管会话复用原 boot 进程回执和完成握手中的准确 thread；原终端 ID 变化仍要求新的可见身份关联。恢复与 `/cd` 不因桌面改显 B 而替换 A；所选会话失效时生成明确微信回执，不自动改投或重发。
- 任务接收时冻结目标、原生队列、仓库准入、订阅角色与 unknown 不重放保持原契约。没有增加依赖或改变数据库 schema。

## 真实原生验收

2026-11-07 10:42，本机 Codex TUI／daemon 0.167.0、Python 3.14、iTerm2 官方 SDK 2.30。只使用自建专用终端，在已获准项目执行只读任务；合成微信入站、隔离 SQLite／Outbox，不操作微信客户端，不调用微信发送 API，不直接修改生产账本或部署配置。完整 ID、进程、client／turn 及标记证据仅保存在任务私有目录，公开[机器摘要](wechat-independent-target.json)只保留脱敏结果。

| 验证对象 | 实际操作与结果 |
| --- | --- |
| 初始来源与选择 | 自有 A 完成可见启动握手，准确进程／终端／thread 关联通过；在桌面切换前持久化微信选择 A，并保持原生订阅连接 |
| 同进程 A→B | 在准确自有终端执行原生 `/new`，选择当前 Git worktree，完成 B 的只读标记；PID、启动时间、TTY 与终端不变，A／B 的 thread 不同 |
| 微信目标恢复 | 同一持续原生连接下，重新构造候选控制器，按受管启动证据恢复原 A；桌面显示 B，没有把微信选择替换成 B |
| 隐藏 A 的真实执行 | 合成微信普通消息要求回忆 A 启动标记，未在追问中提供完整值；经候选准入与原生队列，准确 A 的唯一 client 对应一个 completed turn，正确回忆、零工具调用 |
| 无串投或桌面改显 | A 执行前后 B 的完整原生轮次列表相同，终端仍显示 B；没有复制历史、创建替代 thread 或将 B 切回 A |
| 显式切换 B | 候选显式选择 B 后，第二条合成微信任务进入准确 B，唯一 client／turn 与只读标记一致，completed、零工具调用 |
| 终端关闭后的拒绝 | 两个 thread 均 idle、队列为空后关闭自有终端；向仍选中的 B 发新消息，任务数量不变，生成“所选会话无法可靠接入”提示，不被动改投其他 thread |
| 配置和资源 | Codex 配置、项目私有配置、凭据及本项目 LaunchAgent 的摘要前后一致；测试专用端点已清理，没有停止／部署生产桥接 |

第一轮分阶段工具在各阶段断开原生观察连接，真实观察到旧 A 变为 `notLoaded`。候选拒绝原 A，未恢复它或发送业务任务；核对 B 空闲／空队列后清理该轮自有终端。第二轮改用与已选会话桥接一致的持续原生连接，完成上表全部流程。新建 B 的最初 rollout 曾短暂为空，只读对账既有标记后完成，没有重发输入。

## 自测与复现入口

离线回归覆盖：已绑定 A 在页脚变为 B 或缺失时可继续核验；首次关联仍拒绝缺失／不符页脚；PID 失效、查询期间退出、runtime／session／cwd／thread 变化或卸载拒绝；目录刷新保留 A、同目录两个终端不串投、`/cd` 复用 A、不改变已收任务、失败提示与零提交。原订阅交互仍可按准确请求处理，失效绑定不能授予新派发资格。

统一入口：`.venv/bin/python scripts/check.py --report-dir .tmp/<task>/checks`。2026-11-07 10:50，最终 723 项／40.393 秒全部通过、零跳过，编译／依赖／diff／文档通过。初次沙箱运行有 17 项因本机 Unix socket bind 权限受限而失败；正常权限下全量通过，没有跳过或弱化检查。22 份变更的私有原生标识、个人主目录和尾随空格检查零匹配，准确原生 client／turn 与私有证据交叉核对通过。

显式原生复现入口：

```sh
.venv/bin/python -I tests/integration/independent_target_native.py continuous \
  --case-dir .tmp/<fresh-task>/native --confirm-dedicated
```

只允许全新 case，执行过程中持续保持原生连接。动作前登记意图，不重放既有 workflow。异常后先用 `inspect` 只读核对；`cleanup` 仅在准确自有进程、无未知本地任务、原生空闲且队列为空时关闭自有终端，不将清理当作验收通过。

## 剩余边界

- 这里的用户 session 对应独立对话，桥接以具体 thread ID 标识；原生 sessionId 根身份不能代替它。
- 首次发现任意原终端仍依赖准确页脚；本次没有移除首次显示依赖，没有修改状态栏、标题、Hooks 或原生 CLI。
- 连接断开、原 A 卸载、原生换代或来源证据丢失时不保证恢复；失败通知并要求明确选择，不从存档恢复 A。非受管原终端重启后的隐藏绑定也必须重新证明来源。
- 同仓库的桌面 B 若正在执行，A 的新任务仍受既有仓库准入保护；等待不代表目标改成 B。
- 本轮动态场景为同进程 `/new`；没有把它扩写为所有 fork、子线程、多 TUI 或旧版原生客户端均已重新真机验收。身份变化仍由严格的离线边界与既有协议校验拒绝。
- 手机真实传输与日常部署没有在本次执行；本轮验证合成微信接收／选择／执行／回执链路和真实原生运行时，不把生成 Outbox 说成手机已送达。
