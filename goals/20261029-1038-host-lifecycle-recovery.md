## 4. 已确定的用户行为

| 场景／入口 | 必须达到的行为 |
| --- | --- |
| 冷启动时宿主缺席 | 有效私有配置、本人绑定和账本正常时，微信收发先就绪；显示宿主未启动，不因其缺席退出 |
| 冷启动时 daemon 缺席或连接失效 | 微信保持可用，明确原生运行时不可用；后台只读发现／重连既有受支持运行时，不启动后台替代运行时 |
| `/help`、`/projects`、`/status` | 不要求宿主就绪，不拉起 iTerm2；状态准确区分服务存活、宿主连接、会话核验和原生运行时状态 |
| iTerm2 未启动，收到有效 `/sessions`、`/cd` 或 `/new` | 按需通过 macOS 原生启动方式拉起应用一次，等待 API 并核验；就绪后在本次命令时限内继续。`/new` 仍须满足当前目录前置条件 |
| 无效命令、非法项目／目录或未满足 `/new` 前置条件 | 先返回参数／路由错误，不为无效请求启动应用 |
| 应用启动成功但 API／认证不可用 | 返回具体阶段和下一步；不宣称宿主就绪，不创建 Codex，不自动开启 API 或绕过授权 |
| 运行中宿主退出 | 阻止未经新核验的新派发，结束受影响等待并回执；微信收发和可独立运行的原生事件处理继续 |
| 应用自行或由本人重新启动 | 无须重启桥接，自动连接、刷新并重新核验；后台被动恢复只连接已经运行的应用 |
| 本人主动退出应用后没有新会话命令 | 后台不反复拉起、不反复请求系统授权、不刷屏通知 |
| 普通文字／图片在宿主缺席或目标未复验时到达 | 明确拒绝，不隐式拉起、不暂存为待自动执行任务，不退回旧目标 |
| 原会话存活且重新通过完整核验 | 可恢复准确对应的旧选择；不是按项目名、窗口标题、最近活动或列表位置猜测 |
| 原会话消失或身份不一致 | 清除其新派发资格并提示重新选择；窗口／滚屏恢复不视为进程恢复。后续新建沿用 `/cd`、`/new` 的明确请求及现有幂等契约 |
| 宿主可用但 daemon 缺席 | `/sessions` 解释尚无可核验原生会话；`/cd`、`/new` 明确报告原生前置条件不足。应用启动能力不冒充 Codex 任务能力 |
| 接收新目标选择期间另有会话指令 | 立即给出处理中提示或有界等待；禁止无限堆积，不在恢复后自动执行过时的多条切换／创建请求 |

不增加新的必需微信命令。API／授权状态不可准确区分时，回执应写“连接／授权阶段超时，待核对”，不能无证据断言 API 未启用或授权被拒。

## 5. 生命周期、身份与并发契约

### 5.1 生命周期与组件边界

- 用一个小型宿主连接管理入口表达 `not_running`、`connecting`、`verifying`、`ready`、`unavailable` 等实际状态及失败阶段；只有读请求通过、目录刷新完成才进入 ready。授权是否缺失不能确定时保留 unavailable 和准确阶段。
- 分别跟踪宿主连接代次与原生运行时代次。所有宿主使用者从同一入口取得当前连接，重连时一起替换，不能只有目录切换而 starter／App 单例仍指向旧连接。
- 旧代次的请求完成、回调和清理不得写回新代次的连接、目录、选择或状态；回收 reader、socket、失效单例及 owned window 缓存。
- 同一时刻最多一个宿主连接／拉起流程。连接失败按 1、2、4、8、15 秒间隔退避，最大间隔 15 秒；应用缺席只被动检查；授权明确失败，或授权超时但 API 服务仍可响应时，暂停自动认证，显式会话操作允许一次新的有界尝试。授权子进程超时且 API 传输也无响应时，按连接故障退避重连；无凭据探测须禁用授权 UI，不执行 API 操作，不把服务响应当成已授权或已就绪。
- 探活采用 SDK reader／连接关闭事件，并补充最长 5 秒间隔的有界只读检查；不重复全量屏幕采集，不访问未注册项目正文，不让探活与连接恢复互相递归。
- 原生运行时缺席／断连也不得拖垮微信通道；只读重新发现现有运行时、完成原有版本与归属校验后重连。未知协议版本或错误归属不能自动放行。
- 配置非法、本人绑定无效、账本损坏、消费者冲突等不可用前置条件仍按既有错误退出，不把所有错误吞成“降级正常”。不承诺机器睡眠、网络离线或微信认证过期时仍能远程响应。

### 5.2 身份与已有任务

- 新派发仍完整检查终端、PID 及进程启动身份、TTY、当前可见完整 Session ID、runtime、native thread、native session 和项目目录。新连接成功不是这些核验的替代品。
- 若终端 ID 或进程身份变化，作为新端点重新核验。只有证明仍是准确对应的原生会话才允许重新绑定；证据不足保持未选，不通过放宽全局核验规则来“恢复”。
- 刷新旧数字列表，过期编号不得指向新列表中的其他会话；已经接收的任务仍保持原冻结目标，不能迁移到后来恢复或创建的终端。
- 宿主暂时不可用但原生连接仍有效时，保留准确的既有任务／观察订阅及其事件处理。已有绑定订阅的审批／追问继续遵守 AGENTS 中的精确 thread 规则，不能因宿主代次变化一律失效，也不能借此授予新派发资格。
- 原生连接／运行时代次确实变化时，旧审批答复拒绝；订阅恢复必须获得原生确认。重连不得叠加订阅、重复进展或重复终态回执。
- 提交中、排队中或运行中遭遇断连，按现有账本语义保留已知／未知状态并只读对账；不重放任务、取消、审批或创建动作。不清空账本来消除 unknown。
- 原生 RPC 在恢复后仍必须只有一个有序事件消费者；不得为宿主恢复另开竞争的执行队列或事件读取循环。

### 5.3 超时、幂等与资源上限

下列是本项目的验收目标，不是 iTerm2 或微信平台承诺。使用单调时钟和端到端截止时间，禁止每次重试重置预算。

| 对象 | 上限／判据 |
| --- | --- |
| 已入 inbox 的宿主操作命令 | 2 秒内生成进展、忙碌提示或明确失败回执，不能仅增加 selection_pending 后沉默 |
| 单次 macOS 启动／认证子进程 | 8 秒硬截止；超时先终止本项目创建的子进程并回收，最多再用 2 秒确认退出 |
| 单次宿主只读 RPC | 5 秒；故障后不无限等待 SDK 内部 Future |
| 宿主探活发现失效 | 无系统睡眠／调度暂停时，连接关闭立即处理；无关闭事件的无响应在 10 秒内退出 ready |
| 一次命令的宿主就绪、发现、失败清理 | 总计最多 30 秒，30 秒内产生明确阶段结果；业务新会话握手不计入此预算 |
| 新 Codex 可见启动 | 沿用现有 120 秒握手边界，进展已告知；外部创建结果未知时只对账，绝不自动再创建 |
| 宿主恢复 | 应用和 API 均可用、认证有效、原生可用且测试端点有限时，30 秒内完成重连与刷新；不包含等待本人处理系统授权的时间 |
| `/help`、`/projects`、`/status` | 从已入 inbox 到命令回执入 outbox 不超过 2 秒；网络长轮询及微信投递延迟单独记录 |
| 应用未运行且无显式拉起命令 | 连续观察 60 秒，启动次数为 0；并发显式拉起同一波请求的启动次数最多 1 |

- 同步 AppleScript／认证调用不得放在主事件循环中；仅套 `asyncio.wait_for` 或放入无法终止的后台线程不合格。复用现有隔离探测思路，将认证置于可终止子进程；SDK 建连及响应等待在主循环中保持异步、有界。
- 子进程输出有长度限制，cookie／key 不进入日志、命令行、仓库或错误回执；不修改父进程全局认证配置，不结束系统或其他任务的 osascript。
- 同一源消息、同一启动意图最多一次外部创建；启动已发送但无回执时保持 unknown，只读找回。只读发现可在总截止时间内重试，不能把整个 `/cd`、`/new` 作为可重放单元。
- 在同一代次内正确释放命令锁、选择计数和待办；失败回滚及 finally 也必须有界。不能为释放计数而保留实际上仍可提交任务的后台工作。
- 资源有明确所有权，重复重连不积累 reader、后台任务、线程、子进程、连接或待处理命令；正常 stop 能在故障期间完成，不自动停止用户 Codex。
