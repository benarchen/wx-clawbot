# 微信本地 Agent 工作台：产品设计

本文保存设计与验收要求；实际进度与验证状态以仓库 ROADMAP.md 为准。

项目名：wx-clawbot，根目录为 `<project-root>/`。本文定义目标与验收条件，实现进度只见 ROADMAP。

技术实现与数据契约见 [架构设计](architecture-design.md) ；参考交互来自 [截图整理稿](reference/architecture-from-screenshots.md) 及新增会话命令截图。

开发入口：[技术选型](technical-decisions.md) 、[开发契约与验证关卡](development-contracts.md) 、[施工清单](../goals/implementation-plan.md) 。技术选型不改变下列产品验收条件。

## 1. 产品定位

让用户通过微信选择本机项目和 Codex 会话，下达任务、查看进展、回答追问、处理审批、停止任务，并接收可核验的执行结果。

项目服务多个本地仓库，guixu 是首批使用场景之一。微信是远程入口，项目文件仍在电脑原目录，Codex 负责理解与执行，桥接程序负责目标选择、会话控制和可靠回执。

用户已经确认博主方案符合需求；产品目标是吸收其会话操作体验并形成自己的可维护实现，不再以“该类产品是否需要”为前置讨论。

## 2. 用户目标与首版边界

### 已确认

- 跨本机多个项目切换，不限于知识库问答。
- 首版使用 Codex，后续可以增加其他 Agent。
- 桥接服务不自动修改 Codex 全局配置；初始化的具体例外授权以项目 AGENTS.md 为准。
- 支持项目任务的实际执行，包括按授权修改文件、验证，以及符合各项目规则的 Git 操作。

### 六项问答决策

| 编号 | 用户已确认的首版体验 |
| --- | --- |
| D01 | 接入 iTerm2 中已有的 Codex 会话 |
| D02 | 原终端继续运行，微信作为远程入口，电脑与手机使用同一会话 |
| D03 | 切换已有会话，同时可从微信选择项目，在 iTerm2 启动新的 Codex 会话 |
| D04 | 会话忙碌时，微信和桌面专用排队入口使用同一原生队列；停止、查询和交互答复立即处理；原 TUI 按键边界见场景 F |
| D05 | 审批与追问两端同步展示，只接受首次有效答复，另一端同步已处理 |
| D06 | 首批验收项目为 guixu 和 wx-clawbot；先用临时项目测试，再执行获授权的真实任务 |

本项目与 openclaw-local 完全独立；禁止读取、参考、复用或修改其代码、配置、凭据和服务，不安排关联迁移或退役。

### 首版设计范围

- 本人微信与本机服务绑定；已注册项目选择与目录定位。
- 通过微信在 iTerm2 创建新的 Codex 会话、继续与切换；新会话在电脑也可操作。
- 已有 iTerm2 会话发现、单次发送、持续聚焦与退出；原终端保持运行。attach／detach 独立观察桌面任务，不改变执行焦点，不引入排他接管或后台迁移。
- 任务排队、执行进展、结果、追问、审批、取消与错误反馈。
- 服务常驻、状态查询、基础诊断与断线后状态核对。

### 后续扩展

其他 Agent、更多终端宿主、跨 Agent 协作、语音任务、复杂媒体、定时任务、任意外部程序通知 API、团队多人权限与独立 Web UI。首版不建设通用插件市场，也不复制截图中的全部补丁体系。

### IMG01：入站静态图片扩展

本人于 2026-10-28 明确要求按 [IMG01 施工清单](../goals/20261028-1135-image-input.md) 启动施工；2026-10-29 明确将同消息图文后置，本次交付单张静态 JPEG／PNG 输入，结果仍为文本。实际验收见 ROADMAP 及施工记录。

- 图片沿用普通消息的 focus，收到时固定目标；未选择目标时明确拒绝。attach 不授予图片路由资格。
- 单图默认结合当前上下文分析；分开发送的说明是独立任务。同消息图文解析的预留行为为一次任务，含图斜杠文字不同时执行控制命令；该形态不作为本次已交付能力。
- 跨消息不按时间窗拼接，后续说明按其当时选择进入会话；切换 focus 不迁移已收图片。原会话忙碌时沿用原生队列和既有顺序。
- 图片实际输入同一 runtime／thread，由当前模型读取；不以 OCR 摘要、另开视觉会话或自动换模型替代。
- 多图、引用旧图、动态图片及其他媒体不包含在本次扩展。格式、容量、失败处理、生命周期和真实关卡以施工清单为准；缺少真机证据时保持未验证，W08 原关卡不变。

## 3. 用户理解模型

| 概念 | 用户含义 | 示例 |
| --- | --- | --- |
| 项目 | 要处理哪一份本地工作 | guixu、wx-clawbot |
| 目录 | 本次任务在哪里执行 | 项目根目录或其中一个子目录 |
| 会话 | 使用哪段已有对话与任务上下文 | guixu 的性能整改会话 |
| 原终端 | 电脑上承载该会话的入口 | 已打开的 Codex 终端 |
| 任务 | 本次发出的具体工作 | 分析架构、修改脚本并测试 |

项目切换保留各自会话，不将不同项目的历史串成一段。聚焦负责后续消息发给谁，观察订阅负责接收哪个会话的桌面主动任务。进入同一目录不等于继续同一段对话；受管只表示该会话由项目创建管理，不表示隐藏后台运行。

## 4. 命令与交互

完整参数、失败路径和路由规则以架构文档第 6 节为准，本节描述用户体验。

| 目的 | 命令 | 用户看到的结果 |
| --- | --- | --- |
| 查看项目 | `/projects` | 项目别名、可用状态 |
| 切换目录 | `/cd <项目或路径>` | 当前项目、目录、受管会话；失败时保留原选择 |
| 查找会话 | `/sessions [关键词]`、`/ss` | 带稳定会话标识的编号列表；退出持续聚焦 |
| 单次派发 | `/send <序号> <指令>`、`/s` | 指定原终端收到单次任务；当前焦点不变 |
| 持续发给原终端 | `/focus <序号>`、`/f` | 明确显示聚焦对象；后续普通消息发给它 |
| 退出聚焦 | `/unfocus`、`/uf` | 后续普通消息须重新选择目标；既有任务继续 |
| 观察桌面任务 | `/attach <序号>`、`/a` | 订阅该会话后续桌面任务进展、结果与交互；普通消息目标不变 |
| 取消观察 | `/detach`、`/ua` | 只取消观察订阅，保留 focus、已有任务和原终端 |
| 新话题 | `/new [标题]` | 在当前项目启动新的 iTerm2 Codex 会话，并选中该会话 |
| 查进度 | `/status [任务ID]` | 当前目标与运行、等待交互、排队、送达情况 |
| 停止 | `/stop [任务ID]` | 先显示正在停止，确认终态后再显示已停止 |
| 审批 | `/approve <请求ID>`、`/deny <请求ID>` | 只处理对应具体请求，过期请求明确拒绝 |
| 回答追问 | `/answer <请求ID> <回答>` | 回答准确进入原任务 |

序号仅属于最近一次会话列表，不是项目名称或永久 ID。旧列表过期、目标退出或身份变化时要求刷新。不存在目标时不能自动选最近窗口。

用户可通过已定义的短命令操作；首版不开放“自定义命令直接映射任意 Shell”。后续新增别名应映射现有受控动作，执行项目命令仍交由 Codex 按规则处理。

## 5. 典型使用流程

### 场景 A：微信进入项目并推进工作

```text
用户：/cd guixu
系统：当前项目 guixu，目录……，会话 S1，受管模式。
用户：帮我检查脚本中的重复实现，先给建议。
系统：[guixu · S1 · T1] 已接收，开始读取项目规则。
系统：[guixu · S1 · T1] 分析完成，给出文件位置、依据和建议。
用户：落实第二项，并运行项目要求的检查，不提交。
系统：[guixu · S1 · T2] 返回改动、验证和未完成事项。
```

以上为设计示例，不代表已发生任务。用户授权和项目规则贯穿执行；桥接器不因有写权限就自行扩大任务范围。

### 场景 B：切换项目并返回

```text
/cd wx-clawbot
检查微信消息路由实现。
/cd guixu
继续刚才的讨论。
```

wx-clawbot 和 guixu 使用不同会话；回到 guixu 时恢复其上下文。目标项目没有会话时，可从微信启动新会话。若原任务仍在运行，后续任务排队且显示队列位置；其他项目结果始终标注来源，不随焦点改变。

### 场景 C：操作电脑已有终端

```text
/sessions guixu
/send 2 帮我看下当前项目架构
/focus 2
重点分析脚本职责划分。
/unfocus
```

这条链路要求第 2 个会话确实来自原终端，并能观察到与任务对应的结果。聚焦成功后，界面持续标注原终端会话；不能另开一个新会话后仍称“已聚焦原终端”。

### 场景 D：独立观察桌面任务

```text
/sessions
/focus 2
/attach 1
这条普通消息发往第 2 个会话。
/status
/detach
```

本人已于 2026-10-25 选择独立观察订阅。上例中普通消息发往第 2 个会话，同时接收第 1 个会话桌面主动任务的进展、结果和交互；detach 后普通消息仍发往第 2 个会话。重复 attach 同一目标幂等，替换目标明确回显。原生订阅失败保留原观察状态，不能只修改本地标记后声称成功。细则见[命令契约](command-contract-proposal.md)。

### 场景 E：跨项目审批

用户已聚焦 B 项目，A 项目产生审批时，消息仍明确显示 A、任务 ID、请求 ID、具体操作和有效期。用户回复带 ID 的审批命令，决定仅回到 A 的原请求；B 的目标不变。新请求不能沿用过期的“同意”。

同一请求也在电脑端展示。用户先在电脑回答，微信同步显示已处理；先在微信回答，电脑端同步完成。两端同时回答时只接受首次有效答复，即使一端同意、另一端拒绝也不能执行两次；旧按钮或迟到回复提示已处理。

### 场景 F：电脑与微信共同排队

本人于 2026-10-25 确认首版采用专用桌面排队入口，保留原 Codex 客户端与 iTerm2。会话忙碌时，微信普通任务与电脑在单独普通 Shell 提交的 `codex queue` 任务进入同一 daemon 队列，按原生顺序分别执行，分别关联 queue ID、client ID 和 turn。原 Codex TUI 持续显示进展与结果，两端继续处理审批、追问和停止；空闲时可直接在原 TUI 继续对话。

原 TUI 的 Enter／Tab 沿用 Codex 自身行为，不纳入首版统一队列入口。忙碌时要追加独立普通任务，电脑使用专用排队命令；直接在原 TUI 操作可能引导当前任务或使用其本地队列，服务须识别外部输入，不能将合并执行伪报为各任务独立完成。

此选择保留两端统一排队的目标，改变的是电脑忙碌时的提交入口。首版不改造 Codex CLI、不拦截键盘、不修改全局快捷键。后续若要把原 TUI 按键也统一接入，再依据 [桌面排队契约与决策记录](desktop-queue-contract.md) 评估客户端适配、已有终端迁移和版本兼容；历史失败证据保留，不因本次选择改写成成功。

## 6. 回执与可理解性

正常回执最少显示项目、会话、任务标识和当前状态。最终回执包含结果摘要、实际改动、已完成验证、失败或未完成事项；Git 操作发生时附真实提交／标签或同步结果，不仅报告“成功”。

成功分为三个不同事实：任务已被接收、Agent 执行已结束、结果已提交发送。没有手机确认时不宣称用户已读；发送失败不把任务改成执行失败，更不重跑任务。

长任务发送合并后的阶段进展，保留审批和最终结果的发送优先级；长结果分段编号，关键错误不因截断消失。输出遵守中文排版规范，代码、路径和 URL 保持可用。

输入缺少对象、原终端关闭、列表过期、会话繁忙、权限拒绝、网络中断等情况，返回下一步能执行的动作，例如刷新列表、查看任务或重新选择目标。

## 7. 产品约束

- 手机只有微信即可参与已支持的工作流；电脑必须开机、可联网且服务可用。睡眠和离线不承诺继续执行。
- 首版仅本人使用，不自动开放其他微信身份。
- 明确授权的操作直接推进，执行权限请求通过正式交互处理；不把所有文件修改都变成新增人工确认。
- 默认使用当前 Codex 配置所选模型与登录，不自动切换模型；桥接服务不自动修改全局配置。模型费用跟随实际使用路径，不宣称桥接器免费提供模型额度。
- 项目保持原目录和各自规范。guixu 仍按其单写入者、入库与提交规则执行，其他项目使用自己的规则。
- 服务内部协调不能代替对其他终端的真实控制；不声称阻止所有外部文件修改。
- 首版支持多项目切换，建议最多两个活动项目任务；并发、保留期和队列上限属于可调整设计默认值，不是用户已确认的硬指标。

## 8. 首版验收

所有结果必须有真实日志、文件差异、原生会话状态或手机回执等证据。下表不是已经通过的测试。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| P01 | 本人绑定与收发 | 本人消息进入正确账户，未知身份被拒绝，结果发回同一授权对象 |
| P02 | guixu 与 wx-clawbot 切换 | 路径正确、规则分别读取、历史互不混入；返回原项目继续原会话 |
| P03 | 目录边界 | 空路径、不可访问路径、越界符号链接均不切换目标；不改变其他任务 cwd |
| P04 | 会话发现与单次发送 | 列表明确区分原终端与受管会话；send 在指定原终端执行且不改变焦点 |
| P05 | 聚焦与退出 | 连续消息到同一原终端；unfocus 或 sessions 后普通消息不再误投 |
| P06 | 微信启动新项目会话 | 从微信为无会话的注册项目创建 iTerm2 Codex 会话；电脑可见可操作，微信能继续；重复启动请求不重复创建，失败不产生伪成功 |
| P07 | 文件与验证 | 在临时项目实际修改代码并运行测试；按项目规范输出可核对结果 |
| P08 | 两端审批与追问 | 微信先答、电脑先答、同时冲突答复、超时及断线迟到答复均只接受首次有效决定；另一端显示已处理，跨项目请求不串线；追问采用多题单选与自由文本，同题复选后置 |
| P09 | 排队与取消 | 微信与桌面专用入口共享原生队列，独立任务按序各自完成；原 TUI Enter／Tab 边界按场景 F；焦点切换不迁移队列；停止／查询／交互答复立即处理；stop 后有原生终态证据 |
| P10 | 重复与故障 | 重复入站不重复启动；结果发送失败只重发结果；崩溃未知状态不盲目重跑 |
| P11 | 长输出与通知 | 分段有序、来源清楚、错误不丢失；无字符级刷屏 |
| P12 | 配置与数据保护 | 桥接只写 AGENTS.md 记录的本人授权项；本人确认保留的外部配置更新另行留证并建立新只读基线，不构成桥接新增写权限；无凭据／私人会话进入仓库；不改现有服务 |
| P13 | 重启和离线恢复 | 服务恢复后会话可辨识、旧审批失效、未知任务可核对，不以进程存活假装业务恢复 |
| P14 | 多 Agent 扩展边界 | Codex 实现通过统一适配契约；用测试替身验证 unsupported，不安装第二个真实 Agent |

若 P04 至 P06 尚缺宿主接入，只能称“受管会话阶段版本”，不能以它替代包含原终端体验的完整首版验收。

P06 已依据用户选择 B 更新为微信启动新项目会话。P04／P05 同时验证已确认的观察订阅：focus B、attach A 时输入与观察各自独立，detach 后 B 仍是执行目标；订阅失败、过期列表、目标退出和重复 attach 均有明确结果。不能把契约确认当成技术验收通过。

## 9. 产品交付顺序

1. 固定使用决策与技术方案：iTerm2、原会话继续运行、微信新建会话、忙碌排队、双端交互、独立观察订阅、guixu 与 wx-clawbot 验收。
2. 技术可用性验证：在临时项目验证 iTerm2 原会话与微信新建会话、双端首次答复和停止，不先建设大规模配置体系。
3. 主流程实现：多项目、会话目录、命令和任务结果。
4. 可靠性完善：排队、去重、送达恢复、诊断和常驻。
5. 用户验收：按 P01 至 P14 验证；再单独安排现有服务切换和版本发布。

未来增加 Agent 的完成标准是保持用户命令与任务回执一致，同时明确展示能力差异；不要求不同 Agent 的会话历史天然互通。
