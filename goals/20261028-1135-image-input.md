## 4. 用户行为与范围

### 4.1 本次实现

| 场景 | 确定行为 |
| --- | --- |
| 已 focus 后发送一张图 | 形成一个图片任务；没有文字时使用固定的“结合当前上下文分析图片”提示，不擅自添加改文件或执行命令的要求 |
| 同一原始消息含文字和一张图 | 作为一个任务，保留各内容项顺序；先核对真实消息是否提供此形态 |
| 图片和说明分成两条消息 | 按两条独立输入处理；后续说明只有仍指向原会话时才可利用其上下文，不按时间窗合并 |
| 没有执行目标 | 明确提示先选择会话，不排队，不下载附件，不选择最近窗口或 attach 目标 |
| 下载期间切换 focus | 本图片仍归收到它时固定的目标；后续输入使用新 focus |
| 原目标忙碌 | 下载准备完成后进入同一原生队列；同会话后到任务不得越过先收到但仍在准备的图片 |
| 取消准备中或排队的图片 | 准备中撤销后不得提交；排队项须获得原生删除确认；回执沿用现有单次取消语义 |
| 中断运行中的图片任务 | 定向准确 turn，等待真实终态，不回滚此前已发生的效果 |
| 图片不支持或处理失败 | 给本人明确失败类别；不发送缺图任务，不声称模型已经看到图片 |

不增加 `/image` 等必需命令。纯文本原命令与别名继续原样工作；含图片且文字以 `/` 开头时，按图文任务正文处理，不作为 `/approve`、`/stop` 等控制命令执行，避免一条消息产生控制和图片任务两个副作用。

### 4.2 排除项

- 多张图片合并、相册、引用或转发旧图片、图像文件作为普通文件发送、动态图片、视频、语音、文件收发、图片结果回传及图片生成。
- 自动 OCR 外部服务、另开视觉 Agent、额外模型 API、模型切换、图片公开上传、云端中转及通用媒体平台。
- 修改 Codex TUI Enter／Tab、全局模型／配置／认证／Skills／插件；图片仍使用原生队列，不另建任务调度服务。
- 自动补抓、补发或重放历史已过滤图片；上线验收使用本人新发消息。

### 4.3 工程上限与隐私

初始实现上限为单消息一图，仅静态 JPEG／PNG；单张密文和明文分别最多 10 MiB，解码尺寸最多 2000 万像素，单次下载总时限 30 秒，最多两个并发准备任务，附件磁盘预算 256 MiB。以上是本项目设计上限，不宣称为微信或模型限制；G01 如发现运行时更严格的限制，采用较小值并记录证据。需要扩大范围或改变用户行为时先明确变更，不静默降级。

- 接收者、本人身份、群聊排除、稳定消息 ID 和目标检查先于网络下载；非本人消息不下载、不保存正文、不回显其内容。
- 下载仅允许验证过的微信 CDN HTTPS 地址，禁止任意 host、非标准端口、内网／回环地址和未经验证的重定向；CDN 下载不携带 bot Bearer 或其他 API 凭据。
- 流式限制下载字节，实际解码验证格式、完整性、帧数和像素上限；不只相信扩展名、Content-Type 或声明大小。伪装、截断、解密失败、错误填充、动画和超大解码均拒绝。
- 图片与短期下载材料保存在本项目私有运行目录，目录 0700、文件 0600；随机内部文件名、原子写入、防符号链接与路径穿越，不使用消息给出的文件名作为磁盘路径。
- 不把运行图片放入业务项目、源码或 `.tmp/`；任务临时脚本及人工生成的脱敏测试材料使用本项目 `.tmp/image-input/`。可复用小型无隐私 fixture 可正式纳入 tests。
- 日志、终端诊断和正式证据不打印图片内容、下载参数、完整签名 URL、密钥、context token、本人身份或真实 thread。原生历史可能持久保存图片或引用；桥接清理不等于清理 Codex 历史，不承诺撤回模型已读取内容。
- 图片内容是任务数据，不能替代原生审批。无文字图片默认只分析；后续修改仍遵循已有用户指令和目标项目规则。

## 5. 数据与恢复契约

不建设通用媒体框架。将现有文本输入最小扩展为有序 text／image 内容项，纯文本继续兼容原路径；只新增必要附件记录及关联。

| 对象 | 最少需要表达的信息与不变量 |
| --- | --- |
| 入站内容 | 原生消息 ID、有序内容项、私有媒体引用、回复上下文；去重摘要覆盖整个规范化内容，不能只 hash 文本 |
| 冻结任务 | 准确目标及路由版本、原收件顺序、唯一 client ID、内容项与附件 ID；在任何下载 await 前固定归属并登记顺序 |
| 附件 | 所属消息／任务、格式、大小、摘要、私有存储引用及准备／失败／可用状态；签名 URL 和密钥只保留恢复必需的最短时间 |
| 原生提交 | 同一次 `thread/queue/add` 的输入数组同时包含文字和已就绪图片，沿用唯一 client ID；提交意图持久化后调用原生接口 |
| 投递 | 原任务结果独立进入 Outbox；重试回执不重新下载并执行图片任务 |

入站附件元数据与游标在同一事务保存；下载在事务外、事件循环外执行，失败有持久状态。崩溃不能形成“游标前进但没有可核对附件记录”的窗口。文件原子落盘与数据库提交之间使用可核对的准备记录，覆盖半文件、孤儿文件和记录存在但文件缺失三种情况。

恢复只允许对“有完整原目标、尚未尝试原生提交、身份重新核验通过”的待准备任务继续本地准备和首次准入；本清单不允许从普通旧 inbox 自动重放命令。已尝试提交或状态未知者只读对账，不能根据队列里找不到它就推断从未执行。恢复材料失效则明确失败，不自动要求重发已可能执行的任务。

附件至少保留到其模型消费和任务终态可确认。准备中、排队、运行、unknown 和仍有关键未送达结果的附件不因年龄或预算自动删除；预算不足拒绝新图片，保留已有文本及控制能力。已结附件纳入现有显式 `maintain-state` 计划：默认只读，`--apply` 才清理达到保留期的程序自有内容；不另加自动定时删除服务。附件正文按七天设计，必要摘要按三十天设计，受上述保留例外保护。
