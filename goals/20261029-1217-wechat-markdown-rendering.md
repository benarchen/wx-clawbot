## 5. 渲染、分段与交付不变量

### 5.1 出站结构与入口统一

- 保留源文本的 Markdown 结构；普通正文的中文标点及中英文间距处理仅作用于正文节点，不修改语法、链接目标、代码、命令、路径、引号内的字面值或原生错误中的机器可用片段。
- 同一出站内容在入账前完成兼容处理及分段，发送器读取冻结正文，不随新版本再次渲染。清点帮助、状态、项目／会话列表、进展、最终结果、审批／追问及错误入口；重复调用展示函数不能不断添加空段、围栏、编号或转义。
- 不伪造 `parse_mode`、`markdown` 等未核验协议字段；仍沿用已确认的文本发送协议。保留 API 接受与手机实际显示两种证据的区别。
- 帮助按“项目与会话”“任务控制”“审批与追问”分组，每条命令独立成段，命令／参数准确且可复制；`/help` 只展示已有命令，不借机增加功能。状态和会话列表也应有可辨字段和条目。
- 已持久化的历史 outbox、正文摘要、投递尝试和发送结果保持不变。渲染升级只影响新生成回执；重试旧回执发送其原冻结内容，不回填或美化历史消息。

### 5.2 长消息与字面保真

- 优先按段落、标题／列表项、引用块和代码块边界分段，不能只按固定字符位置截断 Markdown；段号、来源和必要修补字符也计入单条上限。
- 保持当前单条本地校验和整体结果上限，核对序列化后的字节数及服务端实际接受范围；不能把字符数等同于 UTF-8 字节数。若需调整传输上限，须有字段及真机证据，不能靠报错反复试探。
- 跨段代码围栏需正确闭合／重开，语言标签保留；修补的展示标记不得混进代码正文。除有明确记录的行尾规范化外，复制代码的缩进、空格、空行、引号、反斜杠和每一字符保持准确。
- 加粗、行内代码、链接及引用跨段时保持语义。超长不可分的单个 URL／代码行等超出单条容量时，使用明确标注的保真片段兼容，说明无法作为单个完整可点击／可复制块展示；不得截断后仍冒充完整内容。
- 同一结果的段落可按已知的展示编号及围栏修补记录重建原始展示正文；不得通过笼统删除全部反引号、空白或列表符来让重建断言“通过”。
- 原有整体截断只在超过既定总上限时发生，继续明示截断、保留关键错误和首尾；未超限样例不得丢内容。未闭合围栏、嵌套／转义标记、emoji 和组合字符不能造成无限循环、异常内存增长或错误解释。
- 排版不建立新的执行队列，不更改任务来源／目标、取消、中断、原生订阅、审批优先级或一次执行语义；展示中的 `/approve`、Shell 命令、HTML 或链接均不会触发相应动作。

### 7.2 自测执行顺序

1. 先补有效回归：旧实现确实破坏段落／Markdown 结构或多入口处理存在问题时失败，不能用错误期望或环境权限失败伪造复现。
2. 对每个 G 检查点运行相关测试；格式兼容依据和预期结果先固定，再修改实现。客户端不支持与实现错误分开记录。
3. 为长消息加入可识别的首／中／尾随机标记，断言完整顺序和逻辑重建；为代码使用固定摘要及逐字断言，不只统计围栏数量。
4. 使用固定种子的边界／混合样例检查渲染稳定性、长度和完整性；压力测试设可复现截止时间并记录平台。未达标先定位，不能只放宽测试或在失败路径丢正文。
5. 集成完成后执行基础入口；实际测试数量非零，记录本次数量。430 项仅是开工前历史基线，不是本项新成绩。

```sh

.venv/bin/python -m compileall -q src tests
.venv/bin/python -m pip check
git diff --check
```

6. 核对现有 CLI help、协议 fixture 和所有本地文档链接。若新增依赖，另验证锁文件可重建，不覆盖用户现有 `.venv`。权限门禁阻止必要本地 socket 等测试时申请具体操作，不跳过后声称通过。
7. 真机前完成脱敏样例、能力对照、发送／收件记录模板及明确操作卡；本人暂时不能配合时继续独立工作，真人关卡保持未验证。
